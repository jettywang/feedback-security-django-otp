# 令牌设备“重新校准后仍不能立即恢复”诊断路径（HOTP / TOTP）

适用版本：django-otp 1.7.5（OTP 逻辑在小版本间稳定，字段名以本版为准）
面向对象：一线支持同事

## 1. 两类设备与三个要盯的概念

- **HOTP（事件型）**：令牌随“按钮次数”推进。服务端状态核心是 `counter`，
  配合 `tolerance`（向前多看几个计数器）。
- **TOTP（时间型）**：令牌随时间步（默认 30 秒）变化。服务端状态核心是
  `drift`（已知时钟偏差，单位为时间步）和 `last_t`（上一次接受的时间步），
  配合 `tolerance`（向过去/未来各看几步，默认 1，即共 3 个码）。
- **上次接受状态**：HOTP 里就是 `counter`（只增，下一个码必须用更大计数器）；
  TOTP 里是 `last_t`（只增，下一个码必须落在更大的时间步）。
  两者都靠“状态只前进”实现重放保护。

## 2. HOTP：counter / tolerance / 上次接受状态如何更新

源码：`src/django_otp/plugins/otp_hotp/models.py:76`（`verify_token`）

- 校验窗口：`for counter in range(self.counter, self.counter + self.tolerance + 1)`
  （`models.py:88`）。即从**服务端当前 `counter` 起，向上**找 `tolerance+1` 个值，
  默认 `counter..counter+5`。**只会向更大的计数器找，永不回头。**
- 命中时（`models.py:89-95`）：
  - `self.counter = counter + 1`：一次性跳到命中值的下一位，
    中间被跳过的码视为已消费（正常“追赶式同步”，见脚本第一部分场景 A）；
  - `throttle_reset` 清零失败计数与失败时间戳；
  - `set_last_used_timestamp` 记录 `last_used_at`；
  - `save()` 落库。
- 未命中时（`models.py:96-100`）：**`counter` 完全不动**，
  只调用 `throttle_increment` 累加一次失败。
- “上次接受状态”即 `counter` 本身：因为它只增，同一个码重复提交必然落在窗口
  下界之前而被拒（重放保护，脚本场景 B）。

要点：**HOTP 没有任何自动重对齐机制**，容差只是一个有限的前向窗口。
设备被按得太多（超出窗口）或设备计数器反而比服务端小（换设备/设备重置）时，
服务端都无法自行恢复。

## 3. TOTP：tolerance / drift / last_t 如何更新

源码：`src/django_otp/plugins/otp_totp/models.py:109`（`verify_token`）
与 `src/django_otp/oath.py:171`（`TOTP.verify`）

- 时间步计算：`t() = ((int(time) - t0) // step) + drift`（`oath.py:148`）。
  每次校验新建一个 `TOTP` 对象并打上当前时间（`models.py:123-124`）。
- 校验窗口：`TOTP.verify` 令 `offset` 遍历 `-tolerance..+tolerance`，
  逐次把 `drift` 试探为 `drift_orig + offset`（`oath.py:191-192`）。
- 重放门槛：`verify_token` 传入 `min_t = self.last_t + 1`（`models.py:126`）；
  任何使 `t() < min_t` 的候选直接跳过（`oath.py:193`）。
- 命中时（`models.py:127-133`）：
  - `self.last_t = totp.t()`：记录本次接受的时间步（只增）；
  - 若 `OTP_TOTP_SYNC=True`（默认开，`models.py:110`），
    `self.drift = totp.drift`：**把本次为匹配而试探出的偏差固化下来**，
    之后就不必再靠容差猜（脚本第二部分场景 A）；
  - 同样 `throttle_reset`、更新 `last_used_at`、`save()`。
- 未命中时（`oath.py:198-199`、`models.py:135-136`）：`TOTP.verify` 会把
  `drift` **还原为原值**，`last_t` 不变，`verify_token` 只累加一次失败。
  即一次失败不会留下“半同步”的脏状态。
- `OTP_TOTP_SYNC=False` 时（脚本场景 E）：容差内仍可能临时通过，
  但 `drift` 不回写，设备其实没被真正对齐，换个时间点可能又失败。

要点：**`drift` 只能在 `tolerance` 窗口内被学习；偏差一旦超出容差，
永远学不会，状态保持不动。**

## 4. 为什么“重新校准后还是不能立即恢复”——三个独立原因

按现场出现概率排序，对应脚本里的复现：

1. **TOTP 的 `last_t` 卡在当前窗口，校准只改 `drift` 不回退 `last_t`**
   （脚本场景 C，最贴合客户描述）。
   重新校准/人工修正的是 `drift`，而重放门槛 `min_t = last_t + 1` 仍然有效。
   用户若在**同一个 30 秒窗口**内拿着校准前的旧码重试，其时间步 `t <= last_t`，
   必然被拒。**等到下一个时间步、用新码提交即恢复**，这就是“不能立即恢复”。
2. **指数退避（节流）尚未到期**。连续失败会累积
   `throttling_failure_count`，所需间隔为 `factor * 2^(n-1)` 秒
   （`src/django_otp/models.py:531`），即 1、2、4、8… 秒。窗口未到时
   `verify_is_allowed` 直接拦截，连码都不校验（脚本第三部分）。
   校准做对了也要等这个窗口过去；一次成功验证才会清零计数。
3. **偏差已超出容差，校准动作根本没生效**。
   - HOTP：设备计数器偏离超过 `tolerance`，或设备计数器落后于服务端，
     `counter` 不会移动（脚本第一部分场景 C/D）。
   - TOTP：时钟偏差超过 `±tolerance` 个时间步，`drift` 被还原、`last_t` 不变
     （脚本第二部分场景 D）。
   这类情况靠“再试几次”无法自愈，需要重新配对或人工纠正状态。

## 5. 正常同步 vs 需要重新配对：判别标准

| 观察 | 可自行恢复（正常同步/等下窗口） | 需要人工干预或重新配对 |
|---|---|---|
| HOTP `counter` | 一次成功后跳到命中值+1 | 多次尝试后**始终不变** |
| HOTP 设备与服务端计数关系 | 设备计数器在服务端窗口 `[counter, counter+tolerance]` 内 | 设备计数器 > 窗口上界，或 < 服务端 `counter` |
| TOTP `drift` | 成功后更新为匹配所需偏差，且后续稳定 | 尝试后**仍是原值**（说明窗口内没匹配上） |
| TOTP `last_t` | 成功后前进到新时间步 | 长期停在 `-1` 或某个旧值不动 |
| TOTP 时钟偏差 | 在 `±tolerance` 步内可被学习 | 偏差 `> tolerance` 步，无法学习 |
| `throttling_failure_count` | 一次成功即归零 | 持续累加，伴随退避锁定 |
| `last_used_at` | 成功后刷新 | 长期为 `null`/陈旧 |

## 6. 现场该观察哪些状态字段（只读，勿取密钥）

**HOTP 设备（管理后台 “State / Throttling / Timestamps” 分区）**

- `counter`：服务端下一个预期计数器（核心）。
- `tolerance`：前向窗口大小，默认 5。
- `throttling_failure_count`、`throttling_failure_timestamp`：失败次数与最近失败时刻。
- `last_used_at`、`created_at`：最后成功时间与创建时间。
- `confirmed`：设备是否处于可用状态（未确认设备不会参与校验枚举）。

**TOTP 设备**

- `drift`：已学习的时钟偏差（时间步数）。
- `last_t`：上次接受的时间步；模型字段存在，后台默认不在表单暴露，
  需通过 Django shell 只读查询。
- `step`、`t0`、`tolerance`：时间步长、起点、容差（默认 30 / 0 / 1）。
- 同样的 `throttling_failure_*`、`last_used_at`、`confirmed`。

只读查询示例（shell，**只打印状态，不打印 key**）：


## 7. 标准化排查步骤（按顺序做，每步都记录上面的字段快照）

1. **先排除节流**：看 `throttling_failure_count` 与
   `throttling_failure_timestamp`。若处于退避窗口，等到
   `factor * 2^(n-1)` 秒过后再让用户重试，避免把“锁定期”误判成“不同步”。
2. **确认设备类型与配置**：HOTP 还是 TOTP；记下 `tolerance`，
   TOTP 额外记 `step`/`t0`。
3. **拍“尝试前/后”两张状态快照**：让用户提交一次当前码，再拍一次。
   - HOTP 看 `counter` 是否前进；TOTP 看 `drift`/`last_t` 是否变化。
4. **TOTP 让用户等一个完整时间步（默认 30 秒）后用新码再试一次**：
   若新码成功、旧码失败，即命中第 4 节原因 1（`last_t` 重放保护），
   属预期行为，向用户解释“需要等码刷新”，无需重新配对。
5. **判断偏差方向与量级**：
   - HOTP：让用户连按若干次后，比较设备实际计数与服务端 `counter` 的差距，
     确认是否超出 `tolerance`、或设备计数器是否反而更小。
   - TOTP：核对设备时钟与服务端时间差，换算成时间步，确认是否超过
     `±tolerance`。
6. **区分“可对齐”与“需重新配对”**：
   - 偏差在容差内：一次成功即自动追赶（HOTP）或学习 `drift`（TOTP）。
   - HOTP 超窗：可由有权限的管理员把 `counter` 人工校到设备当前值附近，
     再用下一个新码验证；无法可靠对齐（设备被重置/疑似密钥不一致）则重新配对。
   - TOTP 超窗：先纠正设备系统时钟（自动时间），把偏差拉回容差内再验证；
     时钟无法纠正或怀疑密钥不一致时重新配对。
7. **收尾**：成功后确认失败计数归零、`last_used_at` 刷新；
   在工单中只留存状态快照与结论，不留存任何密钥材料。

## 9. 一页速记

- HOTP 只向前看 `[counter, counter+tolerance]`，成功则 `counter=命中值+1`，
  失败则原地不动；无自动重对齐。
- TOTP 在 `±tolerance` 内试探 `drift`，成功才回写 `drift` 并把 `last_t`
  推到当前步；失败则 `drift` 还原、`last_t` 不动。
- “上次接受状态”只增：HOTP 是 `counter`，TOTP 是 `last_t`，重复用旧码必被拒。
- 校准只改 `drift`/`counter` 类对齐量，**不会回退重放状态、也不会解除节流**；
  所以同一窗口立即重试可能仍失败，等新码/退避窗口过后再试是关键鉴别动作。
- 偏差超容差、计数器方向相反、或疑似密钥不一致，才走重新配对。
